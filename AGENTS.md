## Устройство репозитория
- `index.html` — лёгкая витрина (лендинг). Игру НЕ загружает.
- `play/index.html` — игровой бандл (esbuild), Three.js r160, fflate и PeerJS. Модели, текстуры и звук лежат в `play/assets/pack/`; асинхронный `play/assets/boot.js` проверяет архив до запуска игры. Самостоятельный HTML создаёт `scripts/build-offline.py`.
- `assets/` — скриншоты и медиа для витрины и README.
- `README.md`, `CHANGELOG.md`, `LICENSE`, `.github/ISSUE_TEMPLATE/`.
- Сборки не нужно собирать: GitHub Pages раздаёт файлы `main` как есть. Локальный сервер и открытый PR сайт не обновляют.
- `docs/ROADMAP_RU.md` — статус открытых пилотов. Это не журнал игрока и не описание live.

## Ограничения
- Лимит GitHub — 100 МБ на файл, предупреждение с 50 МБ. Не вшивай новые крупные ассеты в игровой HTML: клади их в `play/assets/`. Офлайн-сборщик сохраняет потолок 50 МБ; целевой размер — до 40 МБ.
- Формат сохранений — profile v3. Не ломай совместимость сохранений без явного решения владельца и записи в CHANGELOG.
- Не меняй `camp.v` основной серии лагеря (v1), ключи и `v` у `fieldCompanion` и схему сейва без того же решения. Конверт `terra_save` (v7), profile v3 и версии кампании — разные номера.
- Лицензия: все права защищены (© 2026 Команда «Терры»). Не добавляй open-source лицензию и чужие ассеты без указания автора и лицензии в README → «Благодарности».

## Как работать
1. Не пушь напрямую в `main`. Создавай ветку `feature/<кратко>` или `fix/<кратко>`.
2. Открывай pull request с описанием на русском: что изменено, как проверить, есть ли риск для сохранений.
3. Каждое изменение для игроков — строка в `CHANGELOG.md` (раздел «Не выпущено»).
4. Проверка: `python3 -m http.server 8080` → открыть http://localhost:8080/play/ в Chrome, консоль без ошибок, меню и «Новая игра» работают.
5. Если доступны исходники по модулям — коммить их в `src/` вместе со сборкой, чтобы правки были читаемыми. Каталог `src/` и новый бандл не выдумываются: простая правка остаётся в существующих `play/ui/` или `play/art/`.
6. Даже маленькая кнопка идёт через уже существующие обработчики, состояние и геймплей. Заглушка, ложная защита и вторая система мастерства не добавляются. Пустой `gear.armor` жителя в урон не входит; `hurtPlayer` считает защиту только у героя (`p.armor`). Броню жителя не описывай как уже рабочую.
7. В отчёте разделяй живую сцену, файлы, прямоугольники и попадания. Chromium на SwiftShader — программный рендер стола, не GPU устройства. Физический телефон, safe-area, Safari и офлайн проверяются отдельно. Про FPS и отсутствие утечек пиши только после реальных серий 5×60 на GPU.
8. Пока владелец не слил PR и не опубликовал его, не пиши «выпущено» и «готово в игре live». Заметка для помощников в CHANGELOG игрока не ставится.
